2026, open source

AutoForms

Web pages as typed tools for AI agents. A user-side polyfill for WebMCP.

Problem

Browser agents usually see a web page as a huge accessibility snapshot. They spend most of their tokens reading it, then click and type one element at a time. Forms built with React, Vue or custom dropdowns often don't register the values, and the agent can't tell. WebMCP lets sites expose their own tools to agents, but almost no sites do this yet.

What I built

  • A Chrome extension that finds every form on a page, including inputs outside a <form> tag and inside shadow roots. It turns each one into a named tool with a JSON Schema: types, required fields, options and patterns.
  • Support for enhanced dropdowns (select2, Chosen, Tom Select, MUI comboboxes and more). It fills fields the way a person would, reads each value back, and reports the outcome: submitted, validation failed with per-field errors, or needs the user.
  • Result lists returned as structured data (products, jobs, search hits), with automatic "Load more".
  • A local MCP server bridge on 127.0.0.1 that only accepts connections from the extension. Passwords, card numbers and one-time codes are never sent to the agent; the person types them.
  • Forms that already declare WebMCP toolname and tooldescription keep the site's own names.

Result

In a benchmark with a real LLM agent on 30 tasks across 30 public websites, AutoForms solved all 30. It used 1.94M input tokens in total, against 4.41M for Playwright MCP, 5.99M for agent-browser and 6.67M for Chrome DevTools MCP. It also cost the least ($2.22) and took the fewest browser actions (114 against 185 or more).1

Honest limits

Each task ran once, and the same tasks were used during development, so a blind run on new sites is next. Closed shadow roots and cross-origin iframe forms aren't supported. Filtering hidden page text to defend against prompt injection is on the roadmap.

2026, local desktop assistant

ScoutAI

An observe-only, voice-enabled guide for any Windows workflow.

Problem

People follow long manuals for tools like Excel, Power BI or SAP, switching back and forth and missing steps. Agents that take over the mouse are risky in real work. People need to stay in control.

What I built

  • Turns five source types (URLs, PDF, DOCX, Markdown, TXT) into interactive task checklists, using heading-aware BM25 retrieval to find the relevant instructions.
  • Watches the screen with Windows UI Automation, screenshots and Excel workbook context. It re-checks after mouse or window changes and highlights the right controls, but never clicks, types or moves the mouse.
  • Checks progress with deterministic UI rules first, then before-and-after vision checks. A step only counts as done once the change persists, which avoids false positives from flicker.
  • Offline voice commands (Vosk and Windows SAPI) and grounded Q&A through local Ollama models, or Azure OpenAI.

Why it matters

It's private by default: models run on the machine, and screenshots and documents stay local unless you choose Azure OpenAI.

2026, codebase onboarding agent

Cartographer

Evidence-grounded codebase intelligence.

Problem

Joining a new codebase means weeks of tracing who calls what. LLM chat tools help, but they confidently describe code that doesn't exist.

What I built

  • Static analysis first. AST analysis for Python and JS/TS/TSX builds a NetworkX knowledge graph of entry points, callers and dependencies, and traces execution flows with line-level source evidence.
  • Optional LLM explanations over secret-redacted evidence. Claims without a valid citation are thrown away. Search and every analysis page still work with no LLM at all.
  • A React and FastAPI interface with architecture and dependency graphs, change-impact analysis, risk heuristics, a graph-ranked reading path and an onboarding quiz.

Result

All five planned phases are complete, from ingestion to change impact. It ships with a sample repository used in its tests and demos.

2026, model training from scratch

EmbedLab

Compact text-embedding models, from tokenizer to evaluation.

Why

I wanted to understand embeddings end to end instead of only calling an API, and to measure them properly.

What I built

  • A 4-layer Transformer encoder from scratch (256 hidden size, 4 attention heads, 16,000-token vocabulary), sized to train on an 8 GB laptop GPU.
  • A byte-level BPE tokenizer and masked language modelling on WikiText-2, then dropout-based contrastive learning (two views of the same sentence form a positive pair) to produce normalized 256-dimensional embeddings.
  • Retrieval evaluation with Recall@K and MRR, plus a separate MiniLM fine-tuning workflow comparing STS-B similarity before and after training. It supports mixed precision and gradient accumulation.

Honest limits

It's an educational model trained on WikiText-2. It shows the full pipeline and learns useful similarity, but it won't compete with models trained on billions of tokens.
